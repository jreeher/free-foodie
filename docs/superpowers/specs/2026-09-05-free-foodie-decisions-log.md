# Free Foodie Kickoff — Decisions Log (for morning review)

You asked me to keep going overnight and make the recommended call at each fork rather than waiting for you. This is the running list of judgment calls made without your live input, newest first. Full rationale for each is in `docs/superpowers/specs/2026-09-05-free-foodie-kickoff-design.md` (search for ⚠️) and, once implementation starts, in `docs/superpowers/plans/2026-09-05-free-foodie-kickoff.md`.

Nothing here is irreversible — it's all in a git history you can inspect and revert commit-by-commit if any call was wrong.

## Design-phase decisions

1. **Added a `profiles` table + `handle_new_user` trigger** that the kickoff's schema omitted. Without it, the kept `authStore.ts`/`useAuth.ts` break on every login. Kept minimal (no household/preferences fields). Wrote the trigger with `SET search_path = ''` from the start — CLAUDE.md documents Simmer Down getting bitten by omitting this originally.
2. **Added `recipe_import_log` / `recipe_import_cache` tables** — the kept `extract-recipe-url` function needs them for rate-limiting/caching; the kickoff's schema didn't include them.
3. **Added the `recipe-images` storage bucket + policies via SQL migration** — needed by the kept `useUploadRecipeImage` hook; not in the kickoff's schema.
4. **Deleted `app/(tabs)/grocery/`** — leftover Simmer Down screen not in the kickoff's explicit delete list, but has no place in the new 4-tab structure.
5. **Dropped the old recipe-card photo-import feature** (`extract-recipe-image` edge function, `AddRecipeModal.tsx`, `recipes/import.tsx` + `import-review.tsx`) — you approved this explicitly before going to bed (distinct from the new pantry photo-scan feature, which is being built).
6. **Rewriting `lib/hooks/useRecipes.ts` rather than lightly extending it** — the new `recipes` table schema doesn't have `household_id`/`categories`/`tags`/`is_favorite`/`rating`/`season_tags`/`meal_type`/`total_time_minutes`, so most of the existing filter logic doesn't carry over.
7. **`canMakeNow` filter implemented client-side**, not as a Postgres view/RPC — simpler, fine at this app's scale, can move server-side later if needed.
8. **Photo-scan reconciliation**: Claude's detected item names are fuzzy-matched (`ilike`) against the fixed catalog and shown as suggestion chips; unmatched names are dropped rather than used to invent new catalog rows (there's intentionally no catalog-editing UI yet).
9. **App icon/splash assets left as Simmer Down artwork** — new visual branding treated as a separate design task, out of scope for this kickoff.
10. **AsyncStorage query-cache key renamed** `simmerdown-query-cache-v1` → `freefoodie-query-cache-v1` so a device that ran both apps doesn't resurrect stale cached data.
11. **New Supabase project and new EAS project are not created by me** — both require your interactive login/dashboard access. `.env` and `app.config.ts`'s `eas.projectId` are left with clearly marked placeholders.
12. **No rate-limiting on the new `identify-food-items` endpoint** — kickoff didn't ask for one; adding a new log table for a single endpoint felt like scope creep. Flag if pantry-scan abuse becomes a concern.

## Implementation-phase decisions

1. **`lib/stores/authStore.ts` needed a small edit despite being on the "kept unchanged" list.** Its `updateProfile` action referenced `preferences`/`household_id` (Simmer Down household fields, not in the new `profiles` table) and called an `update_user_preferences` RPC that doesn't exist in the new schema — this is a hard TypeScript compile error once `database.types.ts` is rewritten, not a style preference. Narrowed `updateProfile` to just `display_name`, always via a direct `.update()` (no RPC). Consequence worth flagging: CLAUDE.md documents a real `auth.uid()` RLS race condition on React Native that Simmer Down worked around with SECURITY DEFINER RPCs for every profile/household write. That workaround is *not* carried forward here — adding an RPC for a single `display_name` field with no evidence yet that the race actually recurs in this simpler schema felt like scope creep. If display-name saves ever fail silently on-device, that RPC pattern (migration 011 in the old repo) is the known fix.
2. **`database.types.ts`'s `Database` type needed `Relationships`, `Views`, `Functions`, `Enums`, and `CompositeTypes` fields that the kickoff's schema sketch didn't mention and the original Simmer Down type file also lacked.** Discovered while verifying Task 5: `node_modules/@supabase/supabase-js` resolved to 2.103.0 (package.json only pins `^2.45.4` — no lockfile constraint kept it near that floor), and this version's `postgrest-js` generic constraints (`GenericTable`, `GenericSchema`) require every table to declare `Relationships: GenericRelationship[]` and every schema to declare `Views`/`Functions` — without them, `.insert()`/`.update()` calls resolve to "no overload matches" / argument type `never`, even though the runtime call is completely correct (supabase-js's actual HTTP behavior doesn't depend on these compile-time generics at all — this is TypeScript-only breakage). Fixed by adding `Relationships: []` to every table and `Views: { [_ in never]: never }` / `Functions` / `Enums` / `CompositeTypes` at the schema level — the exact idiom Supabase's own `supabase gen types` codegen emits for an empty set. This fix applies to every hook written after this point (Tasks 8–17), not just `authStore.ts` — without it, essentially every mutation hook in the app would have shown spurious type errors. Original Simmer Down's `database.types.ts` never had this fix either, which explains several of the "pre-existing baseline" errors logged below.
3. **`tsc --noEmit` will never show zero errors for this repo, before or after this kickoff.** Confirmed by checking the baseline before touching any type-bearing file: `supabase/functions/**/*.ts` (Deno edge functions, using `Deno` globals and URL imports) can't type-check under the app's Node/RN tsconfig — structural, pre-existing, not something this kickoff introduced or should fix. `lib/theme/colors.ts` also has a pre-existing bug (`darkColors: typeof lightColors` forces every dark-mode hex value to match light mode's *literal* string type, since `palette` is `as const` and `lightColors` has no widening annotation — this has been broken since before the fork). Neither is part of the kickoff's scope. The plan's original "zero errors, repo-wide" verification target in Task 17/18 is being read as "zero *new* errors relative to this baseline" instead.
   - ⚠️ **Correction to this baseline, found after Task 17's deletions shrank the error list enough to surface it:** `app/_layout.tsx` imports `DMSans_600SemiBold` from `@expo-google-fonts/dm-sans`, but the installed package version only exports 400/500/700 weights (confirmed by reading `node_modules/@expo-google-fonts/dm-sans/index.d.ts` directly) — this was in the very first `tsc` run after Task 1 too, just below the `tail -50` cutoff I was piping through at the time, before ~60 files' worth of other errors were deleted in Task 3. Not touched by this kickoff (only the persister-key line in that file was edited) and not fixed, since font imports are outside this kickoff's scope for a file on the "keep unchanged" list. `app/_layout.tsx` already has a 3-second timeout fallback that renders the app regardless of font-load success, so this shouldn't block the app from running — but if the semibold weight looks visibly wrong (falling back to regular/bold) anywhere, this import is why.
4. **`app/(tabs)/submit/` and `app/(tabs)/profile/` each needed their own `_layout.tsx`.** Found by actually running the app in a browser (Task 18's smoke test), not by `tsc`: Expo Router logged `[Layout children]: No route named "submit"/"profile" exists in nested children` because, without a `_layout.tsx`, a folder-based route registers as `submit/index`/`profile/index` rather than plain `submit`/`profile` — which didn't match `_layout.tsx`'s `<Tabs.Screen name="submit">` / `name="profile">`. Every other folder-based tab in this codebase (`recipes/`, and the now-deleted `plan/`, `marketplace/`, `settings/`) already had its own `_layout.tsx`; the plan missed that this is a required convention, not optional, for any tab that's a directory rather than a single file. Fixed by adding minimal `_layout.tsx` files (plain `Stack`, `headerShown: false`, matching `recipes/_layout.tsx`'s pattern) to both folders. Confirmed fixed by reloading and re-checking the console — the warnings disappeared.
5. **Smoke test results:** started the app via `npx expo start --web` (added `.claude/launch.json` for this) and drove it with the Browser tool. Login screen renders with correct "Free Foodie" / "Recipes for what you have" branding, no console errors (only benign RN-Web deprecation warnings: `shadow*` style props, `props.pointerEvents`). Signup screen also renders correctly with the new copy. Could not go further than the auth screens — no real Supabase project exists yet (placeholder `.env`), so sign-in/sign-up can't actually complete, meaning Pantry/Recipes/Submit/Profile screens, the migrations, and the edge functions are **not yet runtime-verified** — only type-checked and read-reviewed. That verification needs to happen once you've created the Supabase project and applied the two migrations.
